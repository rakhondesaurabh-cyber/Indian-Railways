This document outlines the system architecture for the **RailOpt AI Engine**, describing how the frontend interface interacts with the backend optimization service to schedule railway maintenance with minimal disruption.

## Component Breakdown

### 1. Presentation Layer (Frontend)
Built with **React and TypeScript**, the frontend provides a real-time dashboard for the railway operators.
- **Railway Map (`RailwayMap.tsx`)**: Visualizes stations (nodes) and tracks (edges), overlaying active trains and maintenance blocks.
- **Maintenance Selector (`MaintenanceOptionSelector.tsx`)**: Displays the candidate options (e.g., Night Shadow, Daylight) generated by the AI, allowing operators to choose the best window.
- **Emergency Inject (`EmergencyModal.tsx`)**: Allows immediate logging of track failures, triggering real-time re-optimization.

### 2. API Layer (Backend)
Built with **FastAPI**, serving as the bridge between the UI and the heavy-lifting optimization logic.
- **State Endpoints**: `/api/network`, `/api/trains`, `/api/maintenance` serve the current state of the railway ecosystem.
- **Action Endpoints**:
  - `/api/optimize`: Triggers the `run_optimization` function to process current maintenance requests against the train timetable.
  - `/api/emergency`: Directly updates the database with a critical block and synchronously triggers a re-optimization to find a new viable schedule.

### 3. AI Optimization Engine
The core intelligence module (`optimizer.py`), designed to evaluate thousands of potential scheduling combinations.
- **Train Event Simulator**: Calculates theoretical track crossing times based on train routes and speeds.
- **Window Evaluator**: Evaluates a specific maintenance window against the simulated train events to calculate cascading delays (factoring in 20-minute safety buffers and train priorities).
- **Candidate Generator**: Slices the day into slots and categorizes them (e.g., *Night Shadow* [00:00-05:00], *Afternoon Lull*, *Peak*). It produces 3 viable options (Minimal Disruption, Feasible, High Disruption) for each maintenance request.
- **Strategy Builder**: Aggregates the selected options across multiple maintenance blocks into holistic strategies like **Minimal Disruption**, **Urgent Daylight**, and **Corridor Batching**.

### 4. Data Layer
Currently implemented as a local `mock_db.json` generated by `data_generator.py` for rapid prototyping.
- Stores `network` (nodes, edges), `trains` (schedules, priorities, routes), and `maintenance_requests`.
- **Future State**: Designed to be easily swapped with a PostgreSQL/PostGIS database for spatial data and a Redis cache for real-time train telemetry.

## Optimization Workflow

1. **Trigger**: User requests an optimized schedule or injects an emergency.
2. **Simulation**: The engine projects train movements across the network.
3. **Evaluation**: It assesses each possible 24-hour time slot for every requested maintenance block.
4. **Scoring**: Slots are penalized heavily for delaying "High" priority trains (2x multiplier) and rewarded for utilizing empty "Night Shadow" windows.
5. **Formulation**: The engine presents multi-block *strategies* and individual *candidate options* back to the user, comparing metrics (Trains Affected, Delay Mins) against a naive baseline.
